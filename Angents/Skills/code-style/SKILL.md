# cocos_feihong 代码规范

## 使用时机

- 任务涉及 TypeScript、Cocos 客户端代码、类型声明、命名、重构、配置结构、文档或工具目录规范时，先阅读本 Skill。
- 本 Skill 只保留 TS/Cocos 基础规范，不维护专项 Skill 路由长链；命中非 TS/Cocos 基础问题时，按 `AGENTS.md` 本地 Skills 分类和对应 Skill description 选择更具体 Skill。
- 本 Skill 只约束代码写法，不规定需求澄清、计划、TDD、Review 或上传流程；执行方式按 `AGENTS.md` 的快速通道和风险分流。

## 基础要求

1. 思考、回复、Todos、代码注释统一使用中文。
2. 注释、日志统一使用中文，禁止出现乱码。
3. 所有文本文件统一使用 UTF-8 编码，默认 4 个空格缩进。
4. 新建代码文件时，文件头需包含以下信息：
    - `*Author  : XW`
    - `*Desc    : 该类的作用`
5. 每个类都必须有 `desc` 说明，用于说明该类是做什么的。
6. 禁止增加无意义的中转函数、纯转发包装或只用一次的临时变量。
7. 公共逻辑优先提取为独立函数，避免重复实现。
8. 函数、函数参数、属性需要添加中文注释，注释只写一行语义或职责，禁止堆叠多段。
9. 修改函数、函数参数或属性时，同步更新对应注释和调用处说明。
10. 注释只写“是什么”，不写“为什么 / 对齐设计稿 / 原因 / 历史”等理由。
11. 注释避免技术黑话和不通用术语，用常人能懂的描述，禁止 AI 风的语义注释。

## 通用代码规范

1. 单个函数尽量保持单一职责，职责混杂时主动拆分。
2. 优先使用早返回，减少过深的 `if / else` 嵌套。
3. 禁止在业务代码中散落魔法数字与硬编码字符串；公共值应提取为常量、配置或枚举。
4. 布尔命名统一使用 `is`、`has`、`can`、`should` 等前缀。
5. 函数参数超过 6 个时，优先改为对象参数。
6. 非必要不要直接修改函数入参，避免隐式副作用。
7. 调试日志、临时代码、被注释的大段旧代码在提交前必须清理。
8. `public`、`protected`、`private` 函数必须显式声明返回类型；`async` 函数必须显式声明 `Promise<T>` 返回类型。
9. 除第三方库接口和引擎限制外，禁止新增裸 `any`。
10. 条件判断统一使用 `===`、`!==`。
11. 函数没有额外逻辑、只转调一个方法或只被单点调用时，直接内联到调用处；只有多个调用点、生命周期入口或承载真实流程语义时才保留。
12. 常量或配置只在一个调用处使用时，不再包一层局部变量；只有重复使用、表达式过长或需要固定快照时才提取局部变量。
13. 简单线性函数调用优先保持一行；参数只是属性访问、常量、`this`、`null`、字面量等直接值时，不因为参数数量机械拆行。
14. 函数调用只有包含对象字面量、回调函数、复杂表达式、嵌套调用或一行明显难读时才拆成多行。

## TS / Cocos 基础约定

1. 同一模块中的状态字段命名必须统一，禁止同义混用。
2. 事件名、业务键名、字段名应统一管理，避免字符串散落。
3. 可选对象、动态创建对象、外部接口返回值和异步数据必须显式校验。
4. 非展示代码字符串命名应保持稳定，避免同一含义多套名称。

## 类型与命名规范

1. `PascalCase`：类名、类型名、枚举名。
2. `camelCase`：变量名、属性名、函数名、方法名、参数名。
3. 常量使用全大写加下划线，或沿用项目既有常量风格。
4. 文件名与导出主体保持一致，避免同义不同名。
5. 命名要体现真实职责，禁止使用 `data1`、`temp`、`test` 这类无语义名称。
6. `app` 业务逻辑模块中能作为纯类型存在的定义，统一放入 `dts/` 目录，用 `declare namespace Ixxx` 集中管理，业务代码不散落 `export interface/type`。
7. 业务纯类型包括 UI 参数、场景参数、事件参数、存储数据、模块数据、业务回调参数等只描述数据结构的声明。
8. `base`、`fairyGUI`、Cocos 引擎适配、工具内部类型不强制迁移到 `dts/`，跟随对应 `.ts` 模块导出或就近声明。
9. 依赖运行时类、运行时常量、枚举值、生成链路或需要模块导入的映射类型，保留在对应 `.ts` 文件中，不强行搬进 `dts/`。
10. `dts/` 中引用模块类型时优先使用稳定全局类型；确需引用引擎类型时使用 `import("模块").类型`，避免声明文件变成运行时代码入口。
11. `View` 内只允许保留真正私有的展示辅助类型；与 `dts/` 既有状态结构字段重复的参数类型不再另包一层，直接复用或收敛到 `dts/`。
12. 模块默认数据、业务初始值、角色外观和可跨页面复用的数据形状不放在 `View` 私有 `type` 里；优先归 `DB`、配置、公共 `define` 或对应 `dts`。
13. 会被多个页面或模块复用的数据定义必须放公共定义链路，不能绑定在单个 UI 文件。

## 改动原则

1. 优先修根因，不做表面补丁。
2. 保持改动最小化，不顺手修无关问题。
3. 修改结构、命名或配置时，同步更新相关引用与说明。
4. 提交前至少自查一次受影响文件，确认无失效引用、无明显冗余、无残留调试内容。

## 文档与工具目录

1. `doc/` 目录只放面向策划、流程、设计和实现说明的文档，不放约束后续实现的执行规则。
2. 涉及修改执行规则时，更新 `AGENTS.md` 或 `Angents/Skills` 下对应 Skill；只有说明文档内容变化时才同步更新 `doc/` 目录下对应 `.md` 文件。
3. 新增说明文档时文件命名尽量使用中文。
4. `tools/config/` 只放最终产物，例如导出的 Excel、JSON、配置文件，不混入脚本或临时文件。
5. `tools/script/` 只放可直接使用的辅助脚本，按用途分子目录，例如 `tools/script/excel/`、`tools/script/proto/`、`tools/script/lang/`。
6. `tools/test/` 只放测试、检查、断言类脚本，按模块或用途分子目录，例如 `tools/test/server/`、`tools/test/ui/`。
7. 工具目录命名使用英文小写，文件名使用英文加下划线。
8. 脚本路径解析统一从仓库根开始，输出文件写回 `tools/config/` 或其它指定产物目录，不写在脚本所在目录。
9. 新增脚本前先判断是正式工具脚本还是测试脚本，避免在 `tools/script/` 或 `tools/test/` 根目录堆放零散脚本。
