# cocos_jianghu 代码规范

## 使用时机

- 只要任务涉及代码编写、改动、重构、命名、类型声明、配置结构调整，就先阅读本 Skill。
- 只涉及策划文档、说明文档、需求文档检查时，改用 `Angents/Skills/check-doc/SKILL.md`。

## 基础要求

1. 注释、日志、界面文案统一使用中文，禁止出现乱码。
2. 所有文本文件统一使用 UTF-8 编码，默认 4 个空格缩进。
3. 新建代码文件时，文件头需包含以下信息：
    - `*Author  : XW`
    - `*Desc    : 该类的作用`
4. 如非必要，不增加无意义的中转函数或纯转发包装。
5. 公共逻辑优先提取为独立函数，避免重复实现。

## 通用代码规范

1. 单个函数尽量保持单一职责，职责混杂时主动拆分。
2. 优先使用早返回，减少过深的 `if / else` 嵌套。
3. 禁止在业务代码中散落魔法数字与硬编码字符串；公共值应提取为常量、配置或枚举。
4. 布尔命名统一使用 `is`、`has`、`can`、`should` 等前缀。
5. 函数参数超过 3 个时，优先改为对象参数。
6. 非必要不要直接修改函数入参，避免隐式副作用。
7. 调试日志、临时代码、被注释的大段旧代码在提交前必须清理。
8. `public`、`protected`、`private` 函数必须显式声明返回类型；`async` 函数必须显式声明 `Promise<T>` 返回类型。
9. 非第三方库接口、引擎限制、历史兼容边界外，禁止新增裸 `any`。
10. 条件判断统一使用 `===`、`!==`。

## TS / Cocos / FairyGUI 约定

1. 数值、掉落、关卡、商店等可调内容优先配置化，避免直接硬编码在业务逻辑中。
2. UI、背包、任务、战斗等模块之间应通过明确接口、事件或数据结构交互，避免跨模块直接读写内部状态。
3. 同一模块中的状态字段命名必须统一，禁止同义混用。
4. 定时器、事件监听、观察者、Tween、资源加载回调等注册与释放必须成对出现。
5. `dispose` 必须支持重复调用且不产生副作用；释放后的成员引用应及时置空。
6. 涉及存档、读档、奖励发放、道具扣除等关键流程时，必须先校验状态与条件，再执行写入或扣发逻辑。
7. 事件名、配置键、存档字段名、资源路径标识应统一管理，避免字符串散落。
8. `app/module/*/interfaces/I*View.ts` 是**手写**的结构绑定基类，只做字段声明与 FGUI 组件绑定；业务逻辑必须写在继承类中，禁止往结构绑定基类里塞业务。

## 类型与命名规范

1. `PascalCase`：类名、类型名、枚举名。
2. `camelCase`：变量名、属性名、函数名、方法名、参数名。
3. 常量使用全大写加下划线，或沿用项目既有常量风格。
4. 文件名与导出主体保持一致，避免同义不同名。
5. 命名要体现真实职责，禁止使用 `data1`、`temp`、`test` 这类无语义名称。

## 改动原则

1. 优先修根因，不做表面补丁。
2. 保持改动最小化，不顺手修无关问题。
3. 修改结构、命名或配置时，同步更新相关引用与说明。
4. 提交前至少自查一次受影响文件，确认无失效引用、无明显冗余、无残留调试内容。
