# TS / Cocos / FairyGUI 场景参考

本参考用于把 `code-style` 中的通用约束落到当前仓库常见场景里。

## 1. Cocos 初始化与管理器调用

当前仓库存在较多管理器单例与统一初始化入口，新增逻辑时优先沿用现有结构：

1. 管理器初始化放在统一入口，不在多个业务模块重复散落初始化。
2. 需要跨模块访问的管理器，优先沿用现有单例入口，不额外包装无意义转发层。
3. 修改启动、初始化、全局监听逻辑时，必须确认注册与释放、先后顺序、依赖关系。

## 2. UI 与 FairyGUI 分层

当前项目中 FairyGUI 自动生成类与业务类是分层使用的：

1. 自动生成的 `Interfaces/*` 文件只做结构绑定，不直接写业务逻辑。
2. 业务逻辑写在继承类中，例如 `XWindow`、`XComponent` 或具体模块视图类。
3. 修改 UI 字段、组件名、绑定关系时，同步检查生成类、继承类与调用方是否一致。

## 3. 生命周期与资源释放

项目中 `dispose`、事件、定时器、观察者使用频繁，改动时重点检查：

1. 事件监听、定时器、观察者、Tween、网络单元注册后必须有对应释放。
2. `dispose` 需支持重复调用，不依赖“只会调用一次”的假设。
3. 释放成员后应及时置空，避免后续误用旧引用。
4. 若父类已管理某类资源，子类不要重复释放同一资源。

常见高风险点：

1. 只注册不释放，导致页面关闭后仍继续回调。
2. 页面销毁后还持有节点、资源或观察者引用。
3. 在 `dispose` 中新增副作用逻辑，导致重复调用出现异常。

## 4. 配置、常量与事件管理

以下内容不应直接散落在业务逻辑中：

1. 数值常量
2. 事件名
3. 配置键
4. 存档键
5. 资源路径标识

推荐做法：

1. 放入 `define`、配置文件或统一常量模块。
2. 同类常量保持同一文件集中管理。
3. 修改旧常量时，先全局确认引用，不直接在业务层临时兼容多套名字。

## 5. 模块边界

UI、背包、任务、战斗、网络、数据模块间交互时：

1. 优先通过公开接口、事件或明确的数据结构交互。
2. 避免跨模块直接读取或写入内部状态。
3. 若必须穿透调用，应先确认是否已有公共层封装或数据入口。

## 6. 关键业务流程

涉及以下逻辑时，必须先校验，再执行写入或扣发：

1. 存档与读档
2. 奖励发放
3. 道具扣除
4. 红点、状态切换、流程推进

最低要求：

1. 先校验前置条件
2. 再执行状态写入
3. 最后触发表现、提示或后续流程

## 7. 新增类与重构建议

新增或重构类时，优先按以下思路落地：

1. 命名体现真实职责，不使用 `temp`、`test`、`data1` 等无语义名称。
2. 文件名与导出主体保持一致。
3. 公共逻辑提取到独立函数或公共模块，不复制到多个 UI/流程类中。
4. 保持改动最小化，不借本次任务顺手扩散修无关问题。
