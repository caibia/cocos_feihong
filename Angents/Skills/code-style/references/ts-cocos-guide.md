# TS / Cocos 场景参考

本参考用于把 `code-style` 中的通用约束落到当前仓库常见场景里。

## 1. Cocos 初始化与管理器调用

当前仓库存在较多管理器单例与统一初始化入口，新增逻辑时优先沿用现有结构：

1. 管理器初始化放在统一入口，不在多个业务模块重复散落初始化。
2. 需要跨模块访问的管理器，优先沿用现有单例入口，不额外包装无意义转发层。
3. 修改启动、初始化、全局逻辑时，必须确认入口归属、先后顺序和依赖关系。

## 2. UI 与业务分层

当前项目中 UI 逻辑改动先确认业务类、基础 UI 能力和调用方边界：

1. 业务类沿用当前模块已有视图基类和创建入口。
2. 交互、状态刷新和数据请求放在真实业务 owner，不新增只转发包装。
3. 继承 item/list 的组件如果使用 `data`，需要重新声明具体 payload 类型，并保持中文属性注释。
4. 涉及 UI 编辑器配置、页面结构或组件绑定专项时，按 `code-style` 主文使用时机分流。

## 3. 常量、键名与事件管理

以下内容不应直接散落在业务逻辑中：

1. 数值常量
2. 事件名
3. 业务键名
4. 数据字段名
5. 层级常量

推荐做法：

1. 放入 `define`、配置文件或统一常量模块。
2. 同类常量保持同一文件集中管理。
3. 修改旧常量时，先全局确认引用，不直接在业务层临时兼容多套名字。

## 4. 模块边界

基础代码规范只判断命名、类型、目录和调用方向是否清晰：

1. 新增跨模块调用前，先确认已有公开入口，不新增只转发包装。
2. 纯类型结构优先按 `dts/` 规则集中声明。
3. 涉及专项质量问题时，按 `code-style` 主文使用时机分流。

## 5. 关键业务流程

基础代码规范只检查流程代码是否保持清晰、可命名、可追踪：

1. 流程入口命名要体现真实职责。
2. 状态字段、事件名、业务键名和层级常量不要散落。
3. 涉及状态校验、数据归属、写入顺序或表现触发时，按 `code-style` 主文使用时机分流。

## 6. 新增类与重构建议

新增或重构类时，优先按以下思路落地：

1. 命名体现真实职责，不使用 `temp`、`test`、`data1` 等无语义名称。
2. 文件名与导出主体保持一致。
3. 公共逻辑提取到独立函数或公共模块，不复制到多个 UI/流程类中。
4. 保持改动最小化，不借本次任务顺手扩散修无关问题。
