# 跨表关联字段设计参考

## 适用场景

当编辑器字段涉及以下情况时，建议读取本参考：

1. 字段值需要关联其他配置表的主键 ID。
2. UI 需要显示关联表名称，但最终保存值仍为 ID。
3. 字段结构同时包含“关联 ID + 数量”。
4. 需要判断当前设计是否适合继续沿用旧的拆分字段模式。

## 核心原则

1. 优先“显示值与存储值分离”：界面显示名称，落库保存 ID。
2. 优先“选择式录入”而非“手动输入”：能弹窗选就不要只给数字输入框。
3. 优先“结构化字段”而非“平铺字段”：能用对象或对象数组表达，就不要拆成大量 `xxxId1`、`xxxCount1`。
4. 优先“便于扩展”的结构：要考虑后续是否会从单个扩展成多个、从只要 ID 扩展成要数量/权重/概率。

## 推荐设计模式

### 1. 单个关联 ID

推荐示例：

```json
{
  "npcId": 1001
}
```

设计要求：

1. UI 使用联表单选器或弹窗选择器。
2. 列表与表单中显示 `NPC名称` 或 `名称 + ID`。
3. 保存时仍只落 `1001`。

不推荐示例：

```json
{
  "npcId": "1001"
}
```

并且 UI 只有纯文本/纯数字输入框，不展示任何联表名称。

### 2. 多个关联 ID

推荐示例：

```json
{
  "rewardItemIds": [1001, 1002, 1003]
}
```

设计要求：

1. UI 使用支持搜索的多选弹窗。
2. 已选区显示 `道具名` 或 `道具名 + 附加信息`。
3. 保存值保持为 ID 数组。

不推荐示例：

```json
{
  "rewardItemIds": "1001,1002,1003"
}
```

即通过逗号分隔字符串临时表达多选结果。

### 3. 关联 ID + 数量

优先推荐：对象映射结构。

```json
{
  "costItemMap": {
    "1001": 2,
    "1002": 5
  }
}
```

适用场景：

1. 重点是“按 ID 查数量”。
2. 不强调顺序。
3. 不需要同一个 ID 重复出现多次。

次优推荐：对象数组结构。

```json
{
  "costItems": [
    { "id": 1001, "count": 2 },
    { "id": 1002, "count": 5 }
  ]
}
```

适用场景：

1. 需要保留顺序。
2. 后续可能继续扩展 `count` 之外的字段，例如 `probability`、`bind`、`quality`。

不推荐示例：

```json
{
  "needItemId1": 1001,
  "needItemCount1": 2,
  "needItemId2": 1002,
  "needItemCount2": 5
}
```

该设计扩展性差，字段会快速膨胀，也会加重 schema、UI、校验、文档维护成本。

## UI 设计建议

### 单选场景

1. 优先使用联表单选器或选择弹窗。
2. 列表页可显示 `名称（ID）`。
3. 详情页应支持“重新选择 / 清空 / 跳转查看关联信息（如有）”。

### 多选场景

1. 使用“操作选项弹窗多选器”。
2. 支持按 `name` 搜索。
3. 支持显示已选数量。
4. 支持清空与确认。

### ID + 数量场景

1. 不要拆成多个零散输入框长期硬编码在表单里。
2. 推荐提供结构化编辑器，例如“添加一行 -> 选择道具 -> 填数量”。
3. 每一行都应显示关联名称，避免用户只看到裸 ID。

## 数据迁移建议

如果项目里已经存在旧结构：

1. 先在文档中标记为“兼容性保留方案”。
2. 新需求优先落到结构化字段，不再继续扩展旧的平铺字段。
3. 如条件允许，提供一次性迁移脚本或保存时兼容转换。
4. 校验规则中要同时覆盖旧结构与新结构的合法性边界。

## 设计取舍建议

1. 只会有一个关联对象：优先单个 ID。
2. 会有多个关联对象：优先 ID 数组。
3. 每个关联对象还带数量：优先对象映射或对象数组。
4. 后续还会附带更多维度：优先对象数组。

## 最小检查项

1. UI 是否避免了纯手动输入裸 ID。
2. 是否能通过名称搜索关联项。
3. 是否做到显示值与存储值分离。
4. `ID + 数量` 是否使用了结构化字段。
5. schema、validator、reference-service、文档是否全部同步。
