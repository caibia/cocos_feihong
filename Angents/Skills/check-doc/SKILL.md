# 文档检查 Skill

## 使用原则

1. 用户提到“检查文档”“文档规范”“策划检查”“check-doc”等场景时使用本 Skill。
2. 没有明示级别时，默认使用深度检查。
3. 结论从程序实现与交付落地视角出发，不做空泛评价。

## 报告输出规则

1. 检查报告必须保存到源文档所在目录。
2. 报告命名规则：
    - 单文件：`{原文件名}-检查报告.md`
    - 文件夹：`{文件夹名}-检查报告.md`
    - 多文件：`{共同主题}-检查报告.md`
3. 禁止把报告写到其他目录、临时目录或用户目录。

## 检查级别

| 级别 | 参数 | 适用场景 | 要求 |
| --- | --- | --- | --- |
| 快速检查 | `--level quick` | 小功能、局部改动 | 只抓核心缺失项 |
| 标准检查 | `--level standard` | 常规功能开发 | 覆盖主要实现链路 |
| 深度检查 | `--level deep` | 核心系统、大版本 | 全面检查并输出风险 |

## 核心检查维度

1. 目标与范围：是否说清楚功能目标、适用范围、入口与出口。
2. 界面与流程：是否说明页面结构、跳转关系、关闭返回、状态切换。
3. 交互与反馈：是否说明按钮行为、点击结果、灰置条件、提示文案。
4. 数据与配置：是否说明字段、配置表、参数来源、刷新时机、排序规则。
5. 协议与同步：是否说明前后端接口、请求时机、返回结构、推送与刷新策略。
6. 异常与边界：是否覆盖资源不足、条件不满足、弱网断线、重复点击、并发冲突。
7. 性能与实现风险：是否提示大列表、频繁刷新、资源加载、缓存、兼容性问题。
8. 验收与测试：是否提供验收标准、自测案例、回归影响范围。
9. 多语言与 UI 资源：涉及 UI 时，是否说明文案 Key、图片资源、红点、动效、音效。

## 判定规则

1. `✅ 通过`：信息完整，程序可直接据此实现或拆分任务。
2. `⚠️ 建议补充`：已有描述，但不足以直接落地，或存在实现歧义。
3. `❌ 缺失`：关键实现信息没有写，程序无法安全落地。
4. 若文档已明确写明“本期不做”或“此项不需要”，该项可判定为通过，不为凑项强判缺失。

## 检查流程

1. 先完整阅读文档，再按检查级别筛选关注范围。
2. 逐项记录问题，优先标出会阻塞开发、联调、验收的缺失项。
3. 问题描述必须具体，指出“缺什么、影响什么、建议补什么”。
4. 输出报告时按“必须解决 / 建议补充 / 已通过 / 待确认问题”分组。

## 输出模板

```md
# 文档检查报告

## 检查概览
- 文档名称：
- 检查级别：
- 总结：

## 必须解决
- [检查项] 缺失内容

## 建议补充
- [检查项] 建议内容

## 已通过
- [检查项] 通过原因

## 需要确认
- 问题 1
```

## 输出要求

1. 结论必须简洁、明确、可执行。
2. 不输出空洞套话，不重复原文大段内容。
3. 若文档质量较好，也要明确写出已通过项，而不是只写问题。
4. 若缺少原始文档内容或格式不可读，应先说明阻塞原因，再给出可继续检查的前提条件。
