# 文本与多语言规则

## 使用时机

- 新增或修改用户可见界面文案、按钮文字、提示、弹窗、标签、错误提示。
- 修改 `Language.json`、`LanguageMgr.get()`、文本 id 号段或文本参数。
- 新增本地服务端错误码、协议错误 code 或业务提示。
- Review 中需要检查代码是否出现用户可见明文。

## 核心规则

1. 代码里禁止出现用户可见的明文文本。
2. 用户可见界面文案统一写入 `Language.json`，通过 `LanguageMgr.get(id, params)` 读取。
3. 日志分类、协议字段、资源键、UI 控件名等非展示文本可以保留代码字符串。
4. `Language.json` 文本 id 必须按模块分配连续号段，例如登录模块使用 `10000-10050`。
5. 同模块文本不得跨号段散落；新增文本优先使用该模块已有号段。
6. 修改函数、参数或属性导致文案参数变化时，同步更新注释和调用处。

## 服务端错误码

1. 登录、本地服务端相关错误提示默认沿用 `code == Language.json id`。
2. 新增非 0 服务端错误码时，必须同步补齐 `Language.json`。
3. 协议返回错误 code 后，由客户端按 code 读取文本，不在客户端硬编码错误提示。
4. 错误码要表达真实业务状态，不为跑通界面返回无条件成功。

## 自查清单

1. 是否有用户可见中文或英文直接写在 `.ts` / `.js` 业务代码中。
2. 新增 id 是否落在模块连续号段内。
3. 删除或改名文案时，是否同步检查所有 `LanguageMgr.get()` 引用。
4. 服务端新增 code 是否有对应 `Language.json` 文本。
5. 文案参数顺序是否和调用处一致。

## 常见错误

1. 把按钮文字、提示语直接写在业务代码里。
2. 新增错误码但忘记补 `Language.json`。
3. 同一模块文本 id 分散到多个号段。
4. 把日志字符串误当成用户可见文案，做无意义迁移。
5. 修改文案参数后不更新调用处。
